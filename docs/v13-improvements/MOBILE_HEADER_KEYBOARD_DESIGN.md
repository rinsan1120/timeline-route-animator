## 改修前の構造（当時の静的コード確認／履歴）

- `src/App.tsx`の`topbar`は、ロゴ画像と3つの制作モードボタンを常時表示。狭い幅ではCSSで折り返し、上部の使用面積が大きい。
- `src/styles.css`では幅760px以下のヘッダーが`flex-wrap: wrap`、モードボタン群が`width: 100%`となる。プライバシー案内は独立した帯。
- 3モードのUI文字列は`WORKSPACE_MODE_COPY`、移動実績参照のボタンはJSONファイル選択、計画／スポットのボタンは既存切替関数を使用。
- モード中の地図／映像切替はヘッダーではなく`workspace-view-bar`上にあり、変更対象外。
- `MobileBottomSheet`は3モード共通。可視領域について`visualViewport.height`をシェルに反映するが、フォーカス中の入力欄に合わせたシート展開・内部スクロール制御は現状ない。
- `src/App.tsx`の地点ラベルは`#annotation-label`の**1行text input**（textareaではない）。DAY補足入力`#day-marker-note`、スポット画像の`#spot-label`も類似する入力系。

## #3：確定した画面切替と実装上の推奨詳細（2026-10-16）

- **プロダクトオーナーが承認した画面方針**：スマホの**初期画面では現在の大きなロゴと3モード案内を維持**し、編集開始後は**現在モード名＋コンパクトなブランド表示＋「モード」メニュー**へ切り替える。PCヘッダーはそのまま。
- 現行実装に基づく**初期画面判定の具体化**：`workspaceMode === 'timeline' && points.length === 0`を初期画面とする。計画／スポットへ移ったら地点0件でも編集作業画面と扱う。移動実績のルート／作業を読み込んで地点が存在する場合は編集画面。地図／映像タブの移動では切り替わらない。
- コンパクト時のブランドは横長画像の極端な縮小を避け、テキスト`Journey Map Studio`を表示する実装を推奨。従来の大きなロゴ画像は初期画面で保持する。正式なモード名は必ず`WORKSPACE_MODE_COPY`を再利用する。
- 編集画面のコンパクトヘッダーはブランド文字＋現在モードを左の上下2行、右に44px以上の「モード」ボタンを並べる**横1段の構成**を第一案とする。目安高さ52〜60px。メニューは上端からのドロップダウンで、開いている間だけ作業領域上に重ねる。
- **実装範囲を分離する**：キーボード対応（#14）、未保存確認（#1）、スマホ場所検索の非表示（#17）、STEPパネル改変（#15）は別Issue・別コミットとして実施。

## #3：コンパクトヘッダー推奨仕様

### モバイル（既存の760px以下判定）

1. 通常の編集画面では**1段ヘッダー**を基本とし、左側に視認可能なコンパクトなブランド表示、中央またはブランド下に現在の制作モード名、右端に「モード」メニュー開閉ボタンを置く。高さ目標は**約52〜60px**。高さは端末の文字拡大・safe areaによって柔軟に増やすが、3つの制作モードボタンを常時並べない。
2. 現在のモードは`WORKSPACE_MODE_COPY`から正式名称を表示する。異なる名前を別途ハードコードしない。
3. 「モード」押下で、既存3モードの正式名称＋簡単な説明をタップしやすい形で表示。メニューは通常の地図／映像を覆う一時的なレイヤーとし、閉じれば画面高を消費しない。狭い幅でも横スクロールを発生させず、タップターゲット約44px以上を目安にする。
4. メニュー選択時は**既存の3つのハンドラ**を利用する。移動実績参照＝ファイル選択、計画＝計画モードへ、スポット画像＝スポットモードへ。データ初期化や保存仕様をメニュー固有に実装しない。選択後メニューを閉じる。キーボードのEscapeや外側タップで閉じる。フォーカス移動を破綻させない。
5. ブランド表示は**既存のロゴ意匠**を尊重する。ただし横幅が足りないときに読めないほど縮小しない。ロゴ画像をそのまま縮小するか、簡略なテキスト併用にするかは実際の素材寸法を踏まえて決める。新規画像・依存ライブラリは不要。
6. 初期画面の制作モード説明や開始導線は維持する。編集作業中だけ詳細説明の**常時表示**をやめる。既存の初期画面コンテンツを別実装で複製しない。
7. プライバシー案内の意味・表示を維持する。地図／映像切替（`workspace-view-bar`）は別操作としてそのまま残す。
8. PC（761px以上）のヘッダー・モードボタンは現行どおり。

### モバイル端末上のレイアウト境界

- 幅320〜390px、縦／横画面、折りたたみ端末、文字拡大を想定。タッチ領域を削ってまで高さを固定しない。
- サイトロゴ、現在モード、切替メニューが重ならない構造にし、開いたメニューも地図／ボトムシート操作に不要なイベントを残さない。
- Androidの戻る操作・タッチスクロールとメニュー開閉を競合させず、位置履歴や編集中の地点選択をメニュー開閉で初期化しない。

## #14：ヘッダー改修後の文字入力可視性の設計方針（コミット後の記録）

- ヘッダー縮小だけでは**入力欄が見える保証にはならない**。キーボード対応は別実装が必要。
- 対象はまず`#annotation-label`。同じボトムシート基盤を使うDAY補足とスポット画像の入力欄も、局所的な分岐なしに扱える設計を優先する。
- モバイルで入力へフォーカスした場合、ブラウザの実際の可視領域に収まるようにシートの高さを調整し、`.mobile-sheet-content`の**内部スクロール**で入力欄とカーソルをキーボードの上へ持ってくる。
- シートが半開きで高さ不足なら、入力中のみ十分な高さを確保する。通常の閉／半／全状態を永続変更せず、フォーカス終了とキーボード終了時には元の操作状態へ戻す。IMEの変換確定や入力中のクリックで不要なシート縮退を起こさない。
- `visualViewport.height`だけでなく`offsetTop`、画面座標、`safe-area`とヘッダー実測高の関係を確認し、Android Chrome・Samsung Internet・iOS Safariでキーボード位置の推測定数に依存しない方針とする。
- 画面全体の`window.scrollTo`ではなくシート内スクロールを優先。フォーカス対象を見失わないことと、入力・保存ボタンの操作が続けられることを優先する。
- 日本語IME、入力値、Undo／Redo、選択中地点、メニュー切替、プレビュー／MP4／PNG出力、計画／作業JSONを変えない。
- ブラウザ・実機挙動は**未確認**。実装後の使用感はユーザーが評価する。
