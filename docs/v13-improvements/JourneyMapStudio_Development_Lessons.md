## 2. 事例A：映像画面へのDAYマーカー混入（Issue #13）

Issue: https://github.com/rinsan1120/timeline-route-animator/issues/13

### 2.1 確認された現象

AndroidでV1.3の映像画面を表示した際、映像の外側に編集地図側の巨大なDAYマーカーが重なって表示された。ユーザー提供画面に基づく現象であり、実機での独立再現は未実施。

### 2.2 コードから確認できる手がかり

`src/map/DayMarkerOverlay.tsx` は一部のDAY要素に `visibility: visible` を明示的に設定する。親側の地図画面を `visibility: hidden` で隠しても、子要素の指定によって表示が残り得る。**この組み合わせが実際の直接原因かは修正時に確定すること。**

### 2.3 なぜなぜ分析（原因仮説）

1. **なぜ映像画面にDAYマーカーが出た？** 地図側の表示要素が映像画面に残った可能性がある。
2. **なぜ非アクティブ側の要素が見えた？** 親の `visibility` と子の明示的な `visibility: visible` の組み合わせにより、隠蔽が保証されなかった可能性がある。
3. **なぜその構造を許した？** 地図を保持したまま映像へ切り替える際、地図のオーバーレイをまとめて隔離する責務が曖昧だった。
4. **なぜ設計で発見できなかった？** 映像フレームの一致や編集機能に注意が集中し、既存地図のDOM/CSSとの干渉を十分に扱わなかった。
5. **なぜレビューから漏れた？** 「新画面で何を表示するか」は整理したが、「非アクティブ画面で何を表示・操作できなくするか」の設計条件を明文化しなかった。

### 2.4 教訓

**画面切替は、表示する側の設計だけでは完成しない。非表示側のDOM・オーバーレイ・入力イベント・フォーカスまで含めて境界を定義する。**

対応時はDAYだけの場当たり的な対処で済ませず、地図側の地点バルーン、START/GOAL、HUD、編集ハンドルなどが同じ漏出を起こさない構造を優先する。ただし変更は必要最小限とし、地図側の既存描画やプレビュー・MP4の一致を壊さない。

## 3. 事例B：Androidで入力欄がキーボードに隠れる（Issue #14）

Issue: https://github.com/rinsan1120/timeline-route-animator/issues/14

### 3.1 確認された現象

Androidでバルーンの文字入力欄をタップすると、ソフトウェアキーボードは開くが、編集中の入力欄・入力文字が見えなくなる。ユーザー提供画面に基づく現象であり、実機での独立再現は未実施。

### 3.2 コードから確認できる手がかり

`src/components/MobileBottomSheet.tsx` は `visualViewport.height` の変化を参照する。一方、確認した範囲では、フォーカス中の入力欄をキーボード上の可視領域へ維持する専用制御が見当たらない。**これが直接原因とは未確定である。**

### 3.3 なぜなぜ分析（原因仮説）

1. **なぜ入力できない状態になった？** キーボード表示後、入力対象を視認できなくなった。
2. **なぜ入力対象が隠れた？** 可視領域の変化と、シートの高さ・スクロール・フォーカス位置が整合しなかった可能性がある。
3. **なぜ高さへの対応だけでは不足した？** `visualViewport` に対応しても、フォーカスした入力欄の位置が自動的に保証されるわけではない。
4. **なぜ設計で見落とした？** スマホ対応を主に静的レイアウトとタッチ領域として捉え、文字入力中の状態変化を十分に扱わなかった。
5. **なぜレビューから漏れた？** 「タップ→キーボード表示→入力→確定→キーボードを閉じる」という一連の操作フローを設計上の単位にしなかった。

### 3.4 教訓

**モバイルUIは静止画ではなく状態遷移で設計する。** 入力前・フォーカス時・キーボード表示中・入力確定後まで、操作対象が見えて操作できることを要求として扱う。

Android Chromeだけでなく、iPhone Safari、縦横画面、狭い画面、折りたたみ端末も影響範囲として考える。ただし未検証環境での動作を保証したとは書かない。

## 4. 事例C：映像の空白タップで再生が停止する（Issue #19）

Issue: https://github.com/rinsan1120/timeline-route-animator/issues/19

### 4.1 コードから確認した挙動（実機未確認）

`src/video/VideoWorkspace.tsx` の再生中 `onPointerDown` は、ヒット判定に使う矩形を取得するため `player.pauseForSelection()` を呼び、その戻り値からタップ対象を探す。`src/video/useVideoPlayer.ts` の `pauseForSelection()` は内部で `pausePlayback(true)` を呼び、実際に再生停止を行う。このため、編集ガイド表示中に映像の空白部分をタップしても再生停止する可能性が高い。

### 4.2 なぜなぜ分析（コード上の構造は確認済み、意図・実機結果は未確定）

1. **なぜ空白タップでも止まる？** 対象を特定する前に停止処理を実行するから。
2. **なぜ先に停止する？** ヒット判定に必要なバルーン矩形の取得が、停止する関数 `pauseForSelection()` と結合しているから。
3. **なぜ結合した？** 「描画中の状態を固定して選択する」という目的に対し、読み取り操作と状態変更を一つのAPIへまとめたと考えられる。
4. **なぜレビューで漏れた？** 「バルーンをタップして選択できる」という成功経路に注目し、「対象外をタップしたとき何もしない」という非対象経路の振る舞いを仕様化していなかった。
5. **なぜ設計上の漏れが起きた？** 操作イベントの**判定→副作用→結果**の順序を設計レビューの独立した観点として扱っていなかった。

### 4.3 教訓

**ヒット判定などの読み取り処理と、再生停止・選択変更・保存などの副作用を分離する。操作対象の存在を確かめてから必要な副作用を発生させる。** 対象外操作は原則として既存状態を維持する。再生中の描画状態とタップ位置の整合性も維持する。

### 4.4 今後の設計時に確認すること

- 操作対象を判定する前に、再生停止・選択変更・Undo履歴追加・保存などを実行していないか。
- 対象が見つからない場合の動作を明確にしたか（無操作、通知、キャンセルなど）。
- 取得系の関数に隠れた副作用がないか。関数名と実際の責務は一致しているか。
- PointerDown／Move／Up／Cancel、フォーカス変更、画面切替、非同期描画の途中で副作用が発生する順序は適切か。
- 同じ操作が連続・重複した場合も、意図しない変更や二重確定を起こさないか。

## 5. 共通原因と責務

| 観点 | #13 | #14 |
|---|---|---|
| 境界 | 地図画面／映像画面 | ボトムシート／ブラウザ仮想キーボード |
| 見落とし | 非アクティブ画面の隔離 | 入力中の可視性とフォーカス |
| 仕様化すべき条件 | 画面外オーバーレイや操作の遮断 | 入力対象が常に視認・操作できること |
| 主な設計視点 | 拓海・岳・夏希 | 春香・夏希・拓海 |

共通するのは、**新機能単体ではなく既存コンポーネントやブラウザ状態との接合部で問題が発生した**こと。実装者個人の不注意に帰さず、要件整理・設計レビュー・実装指示の段階で境界条件を明示する。

## 10. 追加レビュー知見（v1.2）

### 10.1 編集状態を扱う操作ガードは横断比較する（#24・#25）

- `src/App.tsx` のMP4生成・保存と一部の映像編集操作では、`videoPlayer.isEditingBalloon()` や `editingBalloonId` でドラッグ中の操作を排他する。
- 一方、作業JSON・計画JSONの保存／読込、通常Timeline JSON読込、STEP 2の表示／編集／アニメ範囲切替、上部の地図／映像切替では、同じ編集状態のガードが統一されていない。これは**コード上の条件差**として確認した。
- ただし、ポインターキャプチャや画面終了のキャンセル処理によって防御される経路もあり、実機で不整合が発生したと断定してはいけない。#24・#25は未確認リスクとして登録した。
- **教訓**：同一編集セッションを変更・中断できる全操作について、「開始可能な状態」「確定／キャンセルの境界」「別操作との優先順位」を同じ表で設計する。個々のボタンだけを見て完成としない。

### 10.2 表示ロジックのライブラリ内部実装への依存を記録する（#26）

- `src/video/videoEvents.ts` のイベント可視性判定は `map._camera.transform.clone()` を利用する。現在のコードに実害があるかは未確認だが、MapLibreの公開APIとして保証されない内部構造への依存リスクがある。
- **教訓**：内部APIを使う場合は、必要性、依存バージョン、代替手法のコスト、壊れたときの影響範囲を短く記録する。性能や描画一致を犠牲にして無条件に置換しない。

### 10.3 エラー案内は環境を決めつけない（#27）

- `src/video/renderer.ts` のVideoEncoder非対応エラーはAndroid Chrome更新を案内する。Windows・macOS・iPhone等でも同じ文言になり得るため、コード上の案内文には改善余地がある。V1.3で新規導入されたものとは断定しない。
- **教訓**：ブラウザ種別を判別していないエラーでは、特定OS・ブラウザだけを対処法として案内せず、判定できた非対応機能を説明する。未検証環境の動作保証もしない。

### 10.4 「静的レビュー完了」と「実機動作保証」は別

- 画面境界、スマホキーボード、ドラッグ、地図・映像整合性、MP4中断、タッチ、共通描画、JSON、Undo／Redo、レスポンシブの**10ブロックのコード確認を完了**した。
- 実機・ブラウザ操作、実MP4／PNG比較、負荷測定、複合操作の再現は未実施。未確認リスクはIssueへ残し、確認した事実のように説明しない。
- 詳細は別紙 `JourneyMapStudio_V13_StaticReview_20261016.md` を参照。

## 11. 事例D：ドキュメントの誤ブランチ配置とGitHub Pages公開版の巻き戻り（2026-10-16）

### 11.1 確認された事実

- V1.3の実装・不具合修正は `feature/video-editor-v13` ブランチで進行していた。V1.3の「地図／映像」切替機能もこのブランチに存在した。
- GitHub Actionsの `workflow_dispatch` により、**2026-10-16 11:57頃（JST）**に開発ブランチのV1.3がGitHub Pagesへデプロイ成功していた（[実行履歴](https://github.com/rinsan1120/timeline-route-animator/actions/runs/38843072952)）。ユーザーはその公開URLでV1.3の不具合を報告していた。
- その後、美奈（ChatGPT）が、V1.3向けの `docs/v13-improvements/ISSUE_TRACKER.md` と `MOBILE_HEADER_KEYBOARD_DESIGN.md` を、**開発ブランチではなく `main` に直接作成・更新した**。
- リポジトリの `.github/workflows/deploy.yml` は `main` へのPushをGitHub Pages自動デプロイ対象としている。文書だけのPushでもワークフローが作動し、**13:20頃・13:37頃・13:41頃（JST）に `main` が再デプロイされた**（[13:41の実行履歴](https://github.com/rinsan1120/timeline-route-animator/actions/runs/38851849121)）。
- 当時の `main` にはV1.3の地図／映像切替UIがまだ存在しなかった。そのため、GitHub Pagesの通常公開URLでV1.3の切替ボタンが消え、**公開内容が旧版へ巻き戻った**。V1.3ブランチ自体のコードからボタンが削除されたわけではない。
- 当初、美奈は `main` のコードのみを根拠に「公開版には切替ボタンが未実装」と説明し、**ユーザーによるV1.3公開直後の実機報告・デプロイ履歴と矛盾することを見落とした**。ユーザーの指摘を受けてGitHub Actions履歴を調べ、誤りを訂正した。
- その後、2文書を `feature/video-editor-v13` に配置し、当該ブランチのコミット・進捗に整合する内容へ更新した（`65f70f103`、`f362693a9`）。`main` 側の旧コピーは削除せず、正式統合時の整合対象として残している。

### 11.2 根本原因と責務

**直接原因（確認済み）**：ブランチを明示せず `main` に対してGitHub上の文書作成・更新を行ったこと、およびそのPushによるGitHub Pagesの自動再デプロイ。

**設計・運用上の原因**：

1. ドキュメントの保存先を「どの機能／バージョンを開発しているか」から決めず、デフォルトブランチを安易に正本とした。
2. GitHubの文書更新を「サイトには影響しない軽微な変更」と誤認し、`main`へのPushが配信内容を置き換えることを事前確認しなかった。
3. 開発ブランチのIssue管理表が `main` のみに置かれ、Codexの実作業ブランチに存在しないという不整合を見逃した。
4. 現在の `main` とユーザーが実際に表示していたGitHub Pagesの過去のデプロイ元を混同し、ユーザーの時系列情報よりコードの一断面を優先してしまった。

責任はGitHubやCodexの仕様ではなく、**美奈が行った更新先・公開影響の判断と確認の不足**にある。ユーザーに再確認を繰り返す前に、操作を行った側がデプロイ履歴を確認すべきだった。

### 11.3 再発防止の運用ルール

1. **GitHubへの書込み前に、必ず対象リポジトリ・ブランチ・ファイルパスを確認して明示する。** ブランチ省略によるデフォルト `main` 書込みを避ける。既存機能の作業中は、原則その機能の開発ブランチにドキュメントも保存する。
2. **書込み前に公開への影響を確認する。** `.github/workflows/` の `push` 対象と `workflow_dispatch` の公開先、過去のデプロイ履歴を必要な範囲で確認する。「docsだけなら安全」と決めつけない。
3. **ユーザーの承認なく公開版を入れ替える操作を行わない。** 開発ブランチからの手動Pagesデプロイ中は、`main` へのドキュメント単独コミットも公開版の巻き戻りにつながるため避ける。
4. **ドキュメントの正本は作業実態と一致させる。** V1.3開発中の管理表・設計・開発知見は `feature/video-editor-v13` で更新し、正式統合時に `main` へ反映する。複数ブランチにコピーがある場合は最新版と統合方法を明記する。
5. **調査では「現在のコード」と「実際に配信されたコード」を区別する。** UIが消えた・巻き戻ったという報告では、main/feature差分だけでなく、Actions実行ブランチ、実行時刻、SHA、成否を照合する。実機で何が配信されていたか不明なら断定しない。
6. **GitHubコネクタによる書込みは即座にリモートコミットされる**。Codexのローカル `git commit`（`push`禁止）とは別の操作であり、影響を説明してから対象ブランチに限定する。ローカル作業ツリーとの同期にはユーザー側のFetch／Pullが必要となる。
7. **修正後は対象ブランチに実際にファイルがあることとコミットSHAを確認する。** 他ブランチの文書が存在するだけで作業ブランチでも参照可能とは判断しない。

### 11.4 今回の教訓

**変更内容がドキュメントのみでも、書込み先のブランチ次第で公開アプリは変更される。** リポジトリ管理・CI/CD・制作中バージョンの境界も、DOMやブラウザUIと同じく設計レビューの対象として扱う。

ブランチに関わる操作では、最初に「どのブランチを編集するか」「そのブランチの更新で何がデプロイされるか」「どのブランチが作業の正本か」を確認する。GitHub Pagesの再公開や `main` へのマージはユーザーの判断を優先する。
